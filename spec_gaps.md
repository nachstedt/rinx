# RST / Sphinx Specification Gaps

This file tracks known deviations and missing features relative to the full
[reStructuredText specification](https://docutils.sourceforge.io/rst.html) and
[Sphinx documentation system](https://www.sphinx-doc.org/).

It serves as a living checklist: entries should be updated or removed when
the corresponding feature is implemented.

## Heading Adornments

| Feature | Status | Notes |
|---------|--------|-------|
| Underline-only headings | ✅ Implemented | Level determined by first-encounter order of the adornment character within a document |
| Overlined headings (`===` above **and** below the text) | ❌ Not implemented | Treated as a distinct adornment from an underline-only heading using the same character; currently parsed as two consecutive paragraphs |
| Per-document level reset vs. project-wide level tracking | 🔶 Partial | Levels reset per `parse()` call; Sphinx accumulates heading hierarchy across files linked via `toctree` |
| Inline markup/roles inside heading text (e.g. `` :mod:`x` ``, `**bold**`) | ✅ Implemented | `Node::Heading.text` is `Vec<InlineNode>`, parsed via the same `parse_inline_text` paragraphs use, and rendered via the same `render_inline`. Nav-sidebar labels and the page `<title>` still need a plain `String`, so those are derived via `rusty_sphinx_ast::inline_plain_text`, which flattens markup/links down to their visible text (only for H1 headings, which feed `document_titles`). |

## Tables

| Feature | Status | Notes |
|---------|--------|-------|
| Grid tables (`+---+` / `|` / `=` ASCII art) | ✅ Implemented | `crates/parser/src/table.rs::try_parse_grid_table` → `Node::Table { header_rows, body_rows }`; rendered as `<table>`/`<thead>`/`<tbody>`/`<tr>`/`<th\|td>`. Supports the optional `=` header/body divider and both **column spans** (dropped `\|`) and **row spans** (dropped `-` divider), emitted as HTML `colspan`/`rowspan`. Also supports **hierarchical/nested headers** that introduce a finer column split partway through the table (e.g. a header's second line splitting one top-border column into two sub-columns, as in CPython's `apiabiversion.rst`) — column boundaries are derived from the union of every `+` found anywhere in the table, not just the top border, since a `+` is unambiguously a column marker wherever it appears; a row-block that predates a given split reads as an implicit colspan across the not-yet-split columns. One consequence: a stray/typo `+` not aligned with any other row's structure is silently absorbed as a new column boundary rather than rejected (matches real Sphinx/docutils' own ambiguity here). Every line's overall *width* must still match the top border exactly — a width mismatch is reported as a diagnostic and the block falls back to a paragraph (parser stays error-resilient). Cell contents are parsed as full block-level RST ("a miniature document"). Supporting this required making heading adornment detection reject mixed-punctuation lines like `+---+---+` (only a single repeated punctuation char is a valid section adornment, per spec), so a header-less grid table is no longer mistaken for an overline heading. |
| Simple tables (whitespace-column `===` style) | ❌ Not implemented | — |
| `.. csv-table::` / `.. list-table::` directives | ❌ Not implemented | — |
| `.. table::` (table title/caption/options) | ❌ Not implemented | — |

## Domains

| Feature | Status | Notes |
|---------|--------|-------|
| `py`/`c` domains, `function` object type (`.. py:function::`, `.. c:function::`) | ✅ Implemented | Cross-referenced via `:func:`/`:py:func:`/`:c:func:`. Each domain owns an independent object-type vocabulary (`PyObjectType`, `CObjectType`) — no shared `ObjectType` enum across domains. |
| `py` domain `module` object type (`.. py:module::`) | ✅ Implemented | Cross-referenced via `:py:mod:` (and the bare `:mod:` role, resolved via `default_domain`); unlike `:func:` there is no `:c:mod:` form, since real Sphinx's `mod` role has no C-domain analog. |
| `.. py:module::` options: `:platform:`, `:synopsis:`, `:deprecated:` | ✅ Implemented | Fields directly on `DomainObjectBody::PyModule` (not shared with other object types) and rendered inline as leading `<dd>` paragraphs, since rusty-sphinx has no separate module-index page (real Sphinx's `synopsis`/`platform` mainly populate that page rather than the module's own rendered output). |
| `py` domain `data` object type (`.. py:data::`) | ✅ Implemented | Cross-referenced via `:py:data:`/`:data:` *and* `:py:const:`/`:const:` — real Sphinx has no separate `py:const` directive; `const` is just an alternate role spelling that resolves to the same `PyObjectType::Data` as `data` (`ObjectType::from_role_name` maps both `"data"` and `"const"` to `Self::Py(PyObjectType::Data)`), so both roles link to one `.. py:data::` definition. Python-only, like `mod` — no `c:data`/`c:const`. |
| Multiple signatures per definition directive (several argument lines under one directive) | ✅ Implemented | Sphinx lets one definition directive declare several argument lines, each an independently referenceable alias for the same object, all sharing one docstring — e.g. CPython's `library/socket.rst` (`.. data:: AF_UNIX` / `AF_INET` / `AF_INET6`) and `library/re.rst` (`.. data:: A` / `ASCII`). Previously only the first line was kept: the rest were indistinguishable from body content to `collect_directive_body` and silently became docstring text, so the aliases were never indexed and every reference to one warned. Parsed by `collect_argument_continuation_lines` (`crates/parser/src/blocks.rs`), which peels the continuation lines off *before* the body is collected, stopping at the first blank line, dedent, or option field. Stored as `signatures: NonEmptyVector<String>` on every `DomainObjectBody` variant except `PyModule` (real Sphinx's `module` directive takes exactly one argument), replacing the old single `name`/`signature` fields; `NonEmptyVector` (`crates/ast/src/non_empty_vector.rs`) makes emptiness unrepresentable via a smart constructor taking the first element separately, with validating deserialization like `HashedContent`. The analyzer registers one `domain_objects` key and one `GenIndexEntry` per name while indexing the shared body exactly once; the renderer emits one `<dt id="…">` per name before a single shared `<dd>`, the shape real Sphinx renders. Only the *first* name qualifies the scope (what the body inherits, and what a `py:module` sets as current), mirroring Sphinx's `before_content()`. See the "Multiple Signatures Per Directive" example in `examples/domains.rst`. |
| `.. py:data::` options: `:type:`, `:value:` | ✅ Implemented | Fields directly on `DomainObjectBody::PyData`, parsed by `extract_data_options` (mirrors `extract_module_options`) and rendered inline as leading `<dd>` paragraphs, same rationale as `py:module`'s options. |
| `py` domain `method` object type (`.. py:method::`) | ✅ Implemented | Cross-referenced via `:py:meth:`/`:meth:` (Python-only, like `mod`/`data` — no `c:method`). Nesting a `py:method` (or any domain object) inside a `py:class` body automatically qualifies its cross-reference name with the enclosing class's name (see below); a `py:method` with no enclosing `py:class` is indexed under its own bare/manually-dotted name, same as `py:function`. |
| `.. py:method::` options: `:classmethod:`, `:staticmethod:`, `:abstractmethod:`, `:async:` | ✅ Implemented | Boolean fields on `DomainObjectBody::PyMethod`, parsed by `extract_method_options` (mirrors `extract_module_options`'s flag-scanning loop) and rendered as `<em class="property">` prefix labels before the signature in a fixed `abstractmethod`/`async`/`classmethod`/`staticmethod` order, independent of the order the author wrote them in. `:property:`/`:no-index:` are out of scope (`property` would want its own future `py:property` directive; there's no indexing feature for `no-index` to affect). |
| `.. classmethod::` / `.. staticmethod::` legacy directive aliases | ✅ Implemented | Real Sphinx registers these as `py`-domain directive aliases for `.. py:method::` with the matching option pre-set. The parser resolves them via `DirectiveObjectType::{Classmethod, Staticmethod}` (a parser-local enum independent of `ast::ObjectType`), which dispatch to the same `parse_py_method` as `.. py:method::` with a forced flag OR-ed onto whatever the body's own option lines set. `py`-domain only (a bare `.. classmethod::` under a `c` default domain stays an unknown directive). This is the shape CPython's `zoneinfo` docs use for `ZoneInfo.clear_cache`. |
| `py` domain `class` object type (`.. py:class::`) | ✅ Implemented | Cross-referenced via `:py:class:`/`:class:` (Python-only — no `c:class`). Shares `PyFunction`'s shape (`{ signature, is_final, body }`); `extract_object_name` already strips an optional base-class list (`Greeter(Base)` → `Greeter`) so it needed no changes. `:final:` renders a `final` prefix label before the `class` label (same mechanism as `py:method`'s modifiers); other real-Sphinx options (`:canonical:`, `:no-index:`, etc.) are out of scope. |
| `py` domain `attribute` object type (`.. py:attribute::`) | ✅ Implemented | Cross-referenced via `:py:attr:`/`:attr:`. Python-only, like `mod`/`data` — no `c:attribute` (real Sphinx's C domain has no attribute-object equivalent either). Like `py:method`, benefits from nesting-based qualification when documented inside a `py:class` body (see `examples/domains.rst`'s `Greeter.name` attribute). |
| `.. py:attribute::` options: `:type:`, `:value:`, `:canonical:` | ✅ Implemented | Fields directly on `DomainObjectBody::PyAttribute`, parsed by `extract_attribute_options` (mirrors `extract_data_options`) and rendered inline as leading `<dd>` paragraphs. `:canonical:` (real Sphinx: the fully-qualified name of where the attribute is actually defined, for re-exports) is rendered as metadata only — no alias/cross-reference-redirect semantics, matching the minimal-semantics treatment every other domain option gets here (there's no `:noindex:` anywhere either). |
| `py` domain `exception` object type (`.. py:exception::`) | ✅ Implemented | Cross-referenced via `:py:exc:`/`:exc:` (Python-only — no `c:exception`). Shares `py:class`'s shape (`{ signature, is_final, body }`) and reuses `extract_class_options` as-is, since real Sphinx gives `py:exception` the exact same signature grammar and `:final:` option as `py:class` (base-class list included, e.g. `InvalidNameError(GreeterError)`). Real Sphinx's `:single-line-parameter-list:`/`:single-line-type-parameter-list:` options are signature-line-wrapping hints only — out of scope, like `py:class`'s `:canonical:`/`:no-index:`, since rusty-sphinx does no multi-line signature wrapping at all. |
| `c` domain `macro` object type (`.. c:macro::`) | ✅ Implemented | Cross-referenced via `:c:macro:`/bare `:macro:` (C-only — no `py:macro`, mirroring the `c` domain's own lack of `py:method`/`py:class`/etc. analogs in the other direction). Shares `CFunction`'s shape (`{ signature, body }`) and reuses `extract_c_object_name` unchanged: object-like macros (`PY_SSIZE_T_MAX`, no parens) and function-like macros (`MAX(a, b)`) both extract correctly since macro signatures never carry a return-type prefix to strip. No options. |
| Nesting-based cross-reference qualification (`py:method`/any domain object nested inside a `py:class`/`py:exception` body) | ✅ Implemented | `index_nodes` (analyzer) and `render_domain_object` (renderer) both track the nearest enclosing `py:class`/`py:exception` scope in a shared `rusty_sphinx_scope::PythonScope` (`crates/scope/src/python_scope.rs`) and prefix it onto anything nested inside that body, via `PythonScope::qualify` — this is what keeps the analyzer's index key and the renderer's anchor `id` from ever drifting apart. Composes across arbitrarily many nested classes (`Outer.Inner.method`). `py:exception` joins `py:class` here since exceptions are classes in Python. |
| Module-based cross-reference qualification (`py:function`/`py:class`/etc. documented as a sibling after `.. py:module::`) | ✅ Implemented | Real Sphinx docs (e.g. CPython's `types.rst`) write `py:module` and the objects it documents as *siblings*, not nested underneath it (`py:module` has no indented content of its own) — this surfaced as CPython benchmark warnings like `broken domain object 'types.coroutine'`, since nothing propagated the module name onto sibling objects. Fixed via the module component of `PythonScope` (`crates/scope/src/python_scope.rs`), sequential (document-order, not lexical-nesting) state threaded through `index_nodes` (analyzer) and `render_domain_object` (renderer) via `PythonScope::set_module`, updated whenever a `py:module` is encountered and left in effect for the rest of the document until another `py:module` changes it — matching real Sphinx, where a module stays "current" until changed. `PythonScope::qualify` combines this with the existing class-nesting qualifier (class wins if both apply) and is domain-scoped: it never applies the module to non-`py` domain objects with no enclosing class scope (`c:function`/`c:macro` siblings after a `py:module` are correctly left unqualified). That initial fix only qualified *definitions* (index keys and anchor `id`s); it left *reference* resolution (`render_inline_domain_object_reference`) doing a single lookup on the literal, unqualified role text, so a bare, idiomatic reference such as a `:exc:` role reading just `ZipImportError`, or a `:meth:` role reading just `find_spec` (real CPython docs never spell these out fully qualified) still produced spurious `broken domain object` warnings. Fixed via a tiered reference lookup (now `PythonScope::reference_candidates`, see the target-resolution-order row below), which tries several qualified names in order rather than the single combined qualification a *definition* needs (which only ever has exactly one enclosing scope). More than one tier is needed because a *reference* can be written from inside a narrower scope than the object it targets: a bare `:exc:` role reading `ZipImportError`, written inside `.. class:: zipimporter`'s own body, refers to an exception that itself was only ever module-qualified (a sibling of `.. module:: zipimport`, never nested in the class) — the class-qualified guess misses and must fall through to the module-qualified one before giving up on the bare name. A *third* scoping mechanism was then needed for CPython's most common house style, where a class's methods are documented **flat** — as siblings with dotted signatures (`.. method:: ZipFile.read`) rather than nested inside `.. class:: ZipFile` — and referred to by bare name from a *sibling* method's body (`:meth:`read`` inside `.. method:: ZipFile.open`), which surfaced as `broken domain object 'read' in Doc/library/zipfile`. There is no enclosing `.. class::` body to supply the scope, so nothing pushed `ZipFile`. Fixed via `DomainObjectBody::deduce_local_scope` (in `crates/ast/src/domain_object_body.rs`, shared by `render_domain_object` and `index_domain_object` so anchor `id`s and index keys can't drift), which decides in one place what scope an object's *own body* lives in: `py:class`/`py:exception` lend their full qualified name (as before), while any other `py` object written with a dotted signature lends its own name-prefix for the duration of its body only. This mirrors real Sphinx's `PyObject.before_content()`/`after_content()`, which sets the `py:class` `ref_context` from the signature's name-prefix for every `PyObject` subclass — deliberately *not* a global "unique short name" fuzzy search, which would lose locality for names as common as `read`. `py:module` lends nothing (its dotted name is a package path, not a class prefix; it is not a `PyObject` in Sphinx either), and `c` domain objects lend nothing when no class scope applies. This in turn exposed a latent qualification bug it had previously been masking via a `TargetName` case-folding collision: the qualifier-repeat guard only recognised a name repeating the *whole* qualifier, so `.. method:: Random.seed` nested in `.. class:: Random` under `.. module:: random` (qualifier `random.Random`, name repeating only the bare `Random.`) was indexed under `random.Random.Random.seed`. Fixed by also stripping a repeat of just the qualifier's *last segment* — case-sensitively, so `ZipFile.` is not mistaken for a repeat of `zipfile.` — matching Sphinx's `handle_signature`, which strips the `py:class` `ref_context` off the signature's name-prefix. Together these take CPython's `Doc/library/*.rst` from 9988 to 9483 `broken domain object` warnings.

A second, deeper bug surfaced investigating the highest-occurrence remaining warning, `Doc/library/datetime`'s `'.datetime'`/`'.datetime.strptime'` (leading-dot syntax, still unresolved — see below): the class-repeat guard above was applied to *any* qualifier string, without distinguishing whether that qualifier came from a class or a module. Real Sphinx dedups a signature's dotted prefix only against the enclosing **class** `ref_context`, and always raw-concatenates the **module**. CPython documents class members as column-0 flat dotted siblings (`.. classmethod:: datetime.strptime`, no enclosing `.. class::`, under `.. module:: datetime`) far more often than not, and when a class shares its name with its module (`datetime`/`datetime`, `dis`/`dis`), the old single-string qualifier couldn't tell "the class's own name" apart from "a repeated module name" — it collapsed `datetime.strptime` to `datetime.strptime` instead of the correct `datetime.datetime.strptime`, silently indexing under the wrong key (and, in `datetime.tzinfo`'s case, colliding with the unrelated `tzinfo` *class*). Fixed by replacing the single flattened qualifier string with `PythonScope`, which keeps the module and the class stack as separate fields (module: `Option<String>`, classes: `Vec<String>` of bare segments) so `PythonScope::qualify`'s absorption logic only ever compares a signature's leading segments against the class stack, never the module — the class/module conflation is now structurally impossible rather than guarded against. `effective_qualifier` and the old flat-string `qualify_name` helper were retired; their behavior is now `PythonScope::qualify`. The `:meth:`.open`` leading-dot ("search upward") role syntax that investigation started from is now implemented — see the target-resolution-order row below. Still unresolved there: roles whose type doesn't match the definition's (`:meth:`~random.seed`` pointing at a `py:function`), which real Sphinx also warns about. |
| Target resolution order (leading-dot `refspecific` targets, and the suffix fallback) | ✅ Implemented | Sphinx picks one of two search orders per role target: written plain, the target is tried unqualified first and only then against progressively more of the enclosing scope (`name` → `class.name` → `module.name` → `module.class.name`); written with a leading `.`, the order is reversed (`module.class.name` → `module.name` → `name`) and, if nothing matches exactly, the target is taken as a dotted *suffix* and every indexed object name is searched for it. Before this, the dot was never stripped anywhere — it reached `PythonScope::qualify`, whose `split('.')` produced an empty leading segment and candidates like `datetime..datetime` that no index key can ever contain — and one fixed order (the dotted one) was used for every reference. This was the single highest-frequency class of CPython benchmark warning (`'.datetime'` 57×, `'.time'` 32×, `'.tzinfo'` and `'.datetime.strptime'` 17× each). The dot is now consumed by the parser into `ast::TargetSearchOrder` (`crates/ast/src/target_search_order.rs`, a `#[serde(default)]` field on `InlineNode::DomainObjectReference`, so `.ast` files predating it still load) rather than left in the target text; `PythonScope::reference_candidates` builds the ordered, deduplicated tier list; and `crates/renderer/src/domain_resolution.rs` performs the search, with the suffix fallback served by a lazily built index of every object name keyed by its dot-segment-**reversed** form, turning a suffix query into a prefix range scan instead of a linear pass over ~50k names. Two deliberate deviations from real Sphinx: (1) the requested object type is checked in **every** tier of **both** orders, where Sphinx checks it only for dot-prefixed targets and otherwise takes the first name match whatever its type — so `:func:`Thread.run`` is reported rather than silently linked to a *method*; a consequence is that Sphinx's "only exact matches allowed for modules" rule is not reproduced, since it exists purely to contain that type-blind matching. (2) An ambiguous suffix match does **not** resolve — Sphinx warns and links the first candidate, whereas here nothing is linked and the candidates are named, via `BrokenLinkKind::AmbiguousDomainObjectReference` and the `ambiguous_domain_object_reference` warning kind in the `--warnings-output` sidecar. Reference-side qualification also stopped using `PythonScope::qualify`: that method's `absorb` step (dedup of a repeated class prefix) exists for *definitions*, and on the reference side was only ever a workaround for the missing `class.name`-without-module tier — with the real tier list in place a reference's text is never rewritten before lookup. See the "Target Resolution Order" section in `examples/domains.rst`. |
| `py` domain role-target aliasing (`:exc:`/`:class:` resolving against either a `.. class::` or `.. exception::` definition of the same name) | ✅ Implemented | Surfaced by the CPython benchmark's `xmlrpc.client.rst`, which defines `Fault` via `.. class::` but references it via `:exc:` (and once via `:class:`) — real Sphinx tolerates this because its `py` domain treats `class`/`exception`/`obj` as mutually-resolvable role targets, a small static table, not a dynamic "search everything" mechanism. Implemented by restructuring `ProjectIndex::domain_objects` from a flat `domain:objtype:name` → doc_path map into a two-level `qualified_name → (object_type → doc_path)` map, plus `ObjectType::role_alias_candidates()` (`crates/ast/src/object_type.rs`), an exhaustive match returning the small set of object types a role is also willing to accept (itself first) — `{Class, Exception}` alias each other, every other object type is self-only. `render_inline_domain_object_reference` tries each scope candidate (see the qualification row above) and, within it, each alias candidate, before falling back to the broken-link warning; the rendered anchor always matches the object type that was actually found, not the one the role requested. Real Sphinx's third alias, `:obj:`, is out of scope — no generic "any object type" role is parsed today (`ObjectType::from_role_name` has no `"obj"` arm) — so the alias set is `{Class, Exception}` rather than the full three-way `class`/`exception`/`obj`. |
| Default domain resolution for bare (unprefixed) directives/roles | ✅ Implemented | The default domain is a `rusty_sphinx_library` Bazel attribute (`default_domain`, default `"py"`), resolved once at parse time — not a `rusty_sphinx.toml` setting, since it describes the library's content rather than the consuming site. |
| Object name extraction from C-style pointer return types (e.g. `char *foo(void)`) | ✅ Implemented | `extract_c_object_name` (`crates/ast/src/domain_object_body.rs`, separate from the Python-only `extract_python_object_name`) strips a pointer-return-type sigil (`*`, `**`, ...) glued to the front of the extracted name, e.g. `"char *foo(void)"` -> `"foo"` and CPython's `"PyObject *PyUnicode_FromString(const char *str)"` -> `"PyUnicode_FromString"`. Still not real C declarator parsing — array declarators (`foo[]`), function-pointer declarators, or a `*` with whitespace on both sides are out of scope. |
| Additional object types (`struct`, `member`, …) beyond `function`/`module`/`data`/`method`/`class`/`attribute`/`macro`, and domains beyond `py`/`c` | ❌ Not implemented | `Directive::DomainObject` wraps `DomainObjectBody`, a sum type with one variant per concrete object type (`PyFunction`, `PyModule`, `PyData`, `PyMethod`, `PyClass`, `PyAttribute`, `CFunction`, `CMacro`), each carrying only its own fields — deliberately *not* one shared struct with every domain's options unioned together. `ObjectType`/`PyObjectType`/`CObjectType` remain a separate, lightweight tag vocabulary used by cross-reference roles (which never carry options). Adding a new object type means: a new `DomainObjectBody` variant + accessor arms (`crates/ast/src/domain_object_body.rs`), a new `PyObjectType`/`CObjectType` variant plus a `from_role_name` arm (`crates/ast/src/py_object_type.rs`/`object_type.rs`), a new `parse_*` function (`crates/parser/src/domains.rs`), a new cross-reference role regex + handler (`crates/parser/src/inline.rs`, if the object type has one), and a new match arm in `render_domain_object` (`crates/renderer/src/directives.rs`) — more touch points than the old fully-generic design, traded for no object type ever carrying another's irrelevant options. |
| `preview` subcommand default-domain awareness | 🔶 Partial | `preview` accepts `--default-domain` but always defaults to `py` today; the VS Code extension will eventually need to supply the enclosing library's actual Bazel attribute value. |
| Explicit `` :role:`title <target>` `` override for domain-object roles (`:func:`, `:mod:`, `:data:`, `:const:`, `:meth:`, `:class:`, `:attr:`) | ❌ Not implemented | Already supported for `:term:` and `:ref:` via a shared `split_display_and_target` helper in `handle_inline_match` (`crates/parser/src/inline.rs`); domain-object roles only support the `!`/`~` target-prefix modifiers so far (see Inline Markup section above), not an explicit display-text override. |
| Cross-referencing domain objects (and targets/glossary terms) nested inside tables, lists, or admonition/version-change/seealso bodies | ✅ Implemented | `analyzer::analyze()` recurses into `Node::Table` cells, `Node::BulletList`/`Node::DefinitionList` items, directive bodies, and nested `DomainObjectBody` bodies via `index_nodes()`, not just top-level `doc.nodes` — matching the recursion `render_nodes` already does. Real Sphinx projects commonly nest `.. data::` definitions inside a grid table cell per row (e.g. CPython's `curses.rst` attribute tables); before this, such definitions parsed and rendered correctly but were invisible to the cross-reference index, so `:const:`/`:data:` references to them always rendered as broken links despite the target anchor existing on the page. See the "`py:data` Definitions Inside a Table" example in `examples/domains.rst`. |
| Automatic general-index entries for domain object definitions | ✅ Implemented | Every `Directive::DomainObject` definition automatically registers a `GenIndexEntry` (`crates/analyzer/src/lib.rs`), alongside its `domain_objects` cross-reference key, using its anchor id verbatim so genindex links resolve to the same `<dt id="...">` a `:func:`/`:class:`/etc. role would. Entry text is a simplified `"{qualified_name} ({object_type})"` (e.g. `"Greeter.greet (method)"` or, since module-based qualification was added, `"types.coroutine (function)"`), not real Sphinx's fuller `"coroutine() (in module types)"` phrasing — a deliberate simplification. |
| `.. py:currentmodule::` (sets module context for subsequent cross-referencing without documenting a module itself) | ✅ Implemented | Real Sphinx docs use it mid-narrative (e.g. tutorial chapters, CPython's `Doc/howto/enum.rst`/`Doc/howto/logging-cookbook.rst`) to switch the "current module" without an accompanying `py:module` synopsis block — this was the single highest-frequency CPython benchmark warning (`Doc/howto/enum: 'Enum'` 31×, and 828 occurrences total across 39 currentmodule-bearing files), since without it, a narrative doc with no `py:module` of its own never qualified its bare references against the module a *different* file actually defines them under. Modeled as its own `Directive::PyCurrentModule { module: Option<String> }` (`crates/ast/src/directive.rs`) rather than a `DomainObjectBody` variant, since — unlike `py:module` — it registers no `domain_objects`/`genindex_entries` entry and renders no HTML of its own. Recognized only in the `py` domain (bare `.. currentmodule::` under a `py` default domain, or explicit `.. py:currentmodule::`; a `c`-default-domain bare form or `.. c:currentmodule::` fall through to `Directive::Unknown`, matching the `classmethod`/`staticmethod` alias precedent) via `split_domain_qualified_name`, a helper factored out of `resolve_domain_object_type` (`crates/parser/src/directives.rs`) so both obey the same domain rules. `.. currentmodule:: None` (real Sphinx's reset form, used 3× in the CPython corpus) is resolved to `None` at parse time rather than carried as a magic string, and applied via a new `PythonScope::clear_module` (`crates/scope/src/python_scope.rs`) alongside the existing `set_module`. `index_nodes` (analyzer) and `render_directive` (renderer) both apply it to the shared `PythonScope` exactly like `py:module`'s `is_module` branch already did, just without the index/genindex insertion. See `examples/current_module.rst`. |
